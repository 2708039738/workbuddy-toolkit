# 跨账号记忆共享

这份文档说明 `workbuddy memory` 的实际行为边界：什么内容会被发布给其他账号、什么不会、容量卡在哪里、出问题怎么退回去。

命令速查见[命令参考](command-reference.md#跨账号记忆汇总)，能力索引见[功能参考](feature-reference.md#跨账号记忆汇总--workbuddy-memory)。

## 一句话

默认不共享。开启后，工具把所有账号 `MEMORY.md` 里的**规则**汇总成一个共享库，再把“目标账号自己还没有的”条目追加到该账号文件末尾的受管段落里。账号原文逐字保留，随时可还原。

## 常驻通道与容量

WorkBuddy 客户端按账号读取几个长期记忆文件，单个文件超出上限的部分不会进入上下文：

| 文件 | 单次注入上限 | 适合放什么 | 本工具是否写入 |
|---|---|---|---|
| `MEMORY.md` | 4,000 | 事实、配置、项目状态 | `apply` 在文件末尾追加受管段落 |
| `SOUL.md` | 10,000 | 行为准则、红线、流程 | 只有 `rebalance --apply` 追加受管段落 |
| `USER.md` | 10,000 | 称呼、语言、沟通偏好 | 只有 `rebalance --apply` 追加受管段落 |
| `IDENTITY.md` | 10,000 | 身份元数据 | 不写（不放记忆） |

`memory` 只处理上表这四个**账号级**文件。仓库里没有工作区级记忆通道的读写实现，也没有 shard 分片记忆的处理路径：`collect` / `apply` 不会读也不会写工作区记忆或任何分片。

规划容量时请注意：4,000 是 `MEMORY.md` 的额度，不是 10,000。把 10,000 当成 MEMORY 的可用空间，会得到一份永远被截掉一半的文件。

## 发布分级

`apply` 不是“把库里所有条目搬过去”。每条先定级，默认只发布 P0–P2：

| 级别 | 判定线索 | 默认发布 | 典型内容 |
|---|---|---|---|
| P0 红线 | 密钥 / 密码 / token / 凭证 / 隐私 / 客户信息 / 身份证 / 银行卡 / apikey **且**含禁止类措辞 | 是 | `禁止把密钥写进仓库` |
| P1 显式指令 | 必须、禁止、不要、不得、一律、始终、永远、只能、务必、以后都、叫我、称呼、默认用；never / must / always | 是 | `提交前必须跑单元测试` |
| P2 项目约定 | 提交、测试、分支、命名、格式、流程、步骤、目录、仓库、合并、推送、审查、构建、部署 | 是 | `分支命名用 feat/ 前缀` |
| P3 习惯 | 偏好、喜欢、倾向、简洁、详细、语气、中文、英文、回复风格 | 否 | `偏好简洁回复` |
| P4 事实或推断 | 其余全部，**以及**含“可能 / 也许 / 大概 / 或许 / 之类 / 应该是 / 看情况 / 似乎”等模糊措辞的条目 | 否 | `项目根目录在 D:\work\app` |

两条实现细节值得知道：

- 分级是**纯关键词规则**，顺序是“模糊措辞 → 红线 → 显式指令 → 项目词 → 习惯词”；命中模糊措辞的条目直接落 P4，不再往上看。
- 级别只决定**能不能跨账号**，不参与账号内部择优。你自己文件里的一条路径不会因为“只是 P4”被删掉——它压根不会被删。

### 本机事实一律不跨账号

即使被判成 P0/P1，只要正文里出现下面任一形式，也不会出现在其他账号：

| 形式 | 例子 |
|---|---|
| 本机绝对路径 | `D:\work\app`、`<用户主目录>/proj`、`\\host\share` |
| URL | `https://internal.example.com` |
| 邮箱 | `someone@example.com` |
| UUID | `3f2b8c1e-9d4a-4c7b-8e6f-0a1b2c3d4e5f` |

理由和分级一样：这些是“某台机器上的事”，换个账号就失效，带过去只会误导。

### 预算

共享段落有独立字数预算，默认 **800 字**（`PUBLISH_BUDGET`）：

- 每条按“正文长度 + 3”计（列表符和换行也算）；
- 单次最多 20 条；
- 排序先按级别、再按质量分，所以一条 P0 永远排在措辞更漂亮的 P1 前面；
- 先到先得；装不下的计入“超出预算”，但不会中止整轮——后面的短条目仍可能塞进去；`apply` 会按原因分类打印被跳过的条数；
- `apply --budget 500` 可以临时收紧。放宽通常没有意义——窗口里本来就放不下。

800 不是拍脑袋：分诊后原文约 3,200 字，4,000 − 3,200 ≈ 800。原文越短，共享段落的实际可用空间越大，但预算上限仍是 800。

### 为什么只发布规则，不发布事实

两个原因，任何一个单独成立都足够：

1. **窗口只有 4,000 字。** 事实类条目（路径、项目状态、配置、客户名）数量最多、单条最长。一旦放行，它们会先把别人的原文挤出上下文，而不是“顺便多共享一点”。
2. **跨账号就是跨项目。** A 号记忆里的 `D:/client-x/...`、内部 URL、客户名，到 B 号不但没用，还会让 B 号在错误前提下行动。这不是共享，是污染。

想把偏好带过去，把它写成明确指令：`偏好简洁` 是 P3，不发布；`回复一律不超过 5 行` 是 P1，会发布。

## 命令

| 命令 | 作用 |
|---|---|
| `workbuddy memory` | 等价于 `status` |
| `workbuddy memory collect` | 扫描所有账号 `MEMORY.md`，近重复去重/择优后写入共享库 |
| `workbuddy memory apply [账号]` | 渲染受管段落；省略账号表示全部。追加前会和该账号自有内容比对，已有的不再重复写 |
| `workbuddy memory apply --budget 600` | 临时收紧本次共享段落预算（默认 800） |
| `workbuddy memory rebalance [账号] [--apply] [--target 3200]` | 把准则/画像分流到 SOUL / USER；默认只打印计划 |
| `workbuddy memory forget <关键词或条目 id> [--apply]` | 移出共享库并留墓碑；默认只预览 |
| `workbuddy memory conflicts` | 列出互相否定的规则，以及被压制的另一条 |
| `workbuddy memory status` | 库规模、可发布条数与预算占用、各账号自有/共享字数、是否超 4,000 |
| `workbuddy memory restore <账号>` | 用基线快照还原该账号 `MEMORY.md`，还原前自动备份 |
| `workbuddy memory on` / `off` | 开启 / 关闭切号时的自动汇总与渲染 |

多数子命令支持 `--json`。`on` 会立即跑一次 `collect`，但不会立刻改任何账号文件。

## 典型工作流

**第一步：先看容量，再决定要不要分诊。**

```bash
workbuddy memory status
workbuddy memory rebalance          # 只看计划，不写盘
workbuddy memory rebalance --apply  # 确认后执行；写前备份 MEMORY / SOUL / USER
```

**第二步：汇总并发布。**

```bash
workbuddy memory collect
workbuddy memory apply              # 或 apply <账号> 只处理一个
workbuddy memory apply --budget 600 # 想先小步试水就收紧预算
```

**第三步：处理打架的规则。**

```bash
workbuddy memory conflicts
workbuddy memory forget "不要跑全量测试"          # 先看匹配到哪几条
workbuddy memory forget "不要跑全量测试" --apply  # 确认后移出库
workbuddy memory apply                            # 让共享段落按新库重建
```

顺序不是随便排的：`rebalance` 必须在 `apply` 之前。原文越接近 4,000 字，共享段落剩下的位置越少；原文本身已经超限时，`apply` 会一条都放不进去（输出 `shared 0`）。这时先分诊，再发布。

日常只需要 `workbuddy memory on`。开启后每次切号会先 `collect`，再只给目标账号 `apply`；失败只打印一行提示，不阻断切号。

## 遗忘与墓碑

`forget` 的匹配范围是：条目 id 精确相等，或关键词出现在条目正文里（按规范化文本做子串匹配，忽略大小写与标点差异）。一条关键词可能命中多条，所以默认只预览。

`--apply` 之后：

- 匹配到的条目从共享库移除；
- 同时写入墓碑（`norm` 指纹）；
- 下次 `collect` 不会把它收回来——**即使那段文字还留在某个账号的 `MEMORY.md` 里**，`collect` 会打印“已跳过 N 条被 forget 的条目”；
- 账号文件一个字节都不动。已经渲染进文件的共享段落会保留到下一次 `apply` 重建受管段落时才消失。

墓碑保存在 `cache/shared_memory/library.json` 的 `tombstones` 字段。**目前没有解除墓碑的命令**：确实要恢复某条，只能手动删掉对应墓碑再 `collect`，手改前先备份 `library.json`。

## 冲突压制

典型场景是两条只差一个否定词的规则：

```text
提交前必须跑测试
提交前不要跑全量测试
```

字面相似度会被“不要”拉到 0.90 阈值以下，聚类阶段根本进不了同一簇。所以冲突检测单独做一遍：先把肯定/否定与强度词抹平，再按抹平后的形式分桶。

- 一个桶里至少有一条是否定式，才判为冲突；
- 胜出顺序：级别 → 来源账号数 → 质量分 → 文本；
- 胜者正常注入；败者标 `suppressed`，留在库里备查、不注入、不删除；
- `workbuddy memory conflicts` 列出胜者、被压制的条目和它来自哪些账号；
- 每次 `collect` 都会重算这组标记，不是一次性结论。

工具不替你判断哪条才对。确认后自己 `forget` 另一条；否则败者会一直占着库里的位置，看起来“消失了”，其实还在。

## 并发

切号触发的自动同步和手动命令完全可能同时跑。`collect`、`apply`、`rebalance`、`restore`、`forget` 全程持有 `cache/shared_memory/.hub.lock`（Windows 用 `msvcrt`，类 Unix 用 `fcntl`），进程内可重入——`apply_all` 逐账号调用 `apply_account` 时不会自己把自己锁死。

- 等锁上限 5 秒；
- 超时输出“记忆同步被另一个进程占用，请稍后重试”，退出码 1，不甩 traceback；
- 所有写入都是同目录临时文件 + fsync + `os.replace`，不会留下半截 `MEMORY.md`。

## 什么时候会失效

| 现象 | 原因 | 处理 |
|---|---|---|
| 某账号一直“跳过” | 该账号还没有 `MEMORY.md`（`apply` 显示 `跳过（no_memory_file）`） | 先用客户端正常对话一次，让文件生成 |
| `apply` 显示 `skipped_encoding`，`collect` 显示“跳过（非 UTF-8）” | 文件是 GBK / UTF-16 | 转成 UTF-8。工具不会把读不懂的文件当空文件覆盖 |
| `shared 0`，一条都没注入 | 原文已接近或超过 4,000 字 | 先 `rebalance`，或收紧 `--budget` |
| 某条规则怎么都不出现 | 被判 P3/P4；含路径/URL/邮箱/UUID；被预算挤掉；被冲突压制 | `apply` 会打印跳过原因分类，逐类排查 |
| `forget` 后文件里还看得到 | 只改了库 | 再跑一次 `apply` |
| 切号后没有自动同步 | `memory off`；目标账号无文件；同步异常 | `status` 看开关；同步失败只提示不阻断，重跑 `apply` 即可 |
| 命令卡住 5 秒后报占用 | 另一个进程正持锁 | 稍后重试；不要在切号的同时批量 `apply` |

## 回滚

三层保护，从轻到重：

1. **还原账号文件**：`workbuddy memory restore <账号>`。用基线快照 `cache/shared_memory/originals/<uid>/MEMORY.md` 覆盖账号文件，覆盖前先备份当前文件。
2. **取回某次写入前的副本**：`cache/shared_memory/backups/<账号目录>/<时间戳>.md`，每个目录保留最近 10 份（`rebalance` 一次写入会占掉 3 份）。手动复制回账号目录即可。
3. **停用**：`workbuddy memory off`。它只停止切号时的自动同步，**不会**清掉已经渲染的共享段落；要清还得 `restore`。

几个容易踩的点：

- `restore` 只写 `MEMORY.md`。`rebalance` 搬到 SOUL / USER 的段落不会被删——它们包在 `<!-- memory-rebalance:begin -->` 和 `<!-- memory-rebalance:end -->` 之间，需要时手动删掉这一段。
- `rebalance` 之后直接 `restore`，被搬走的行会同时出现在 `MEMORY.md` 和 SOUL/USER 里：重复，但不丢数据。先想清楚留哪边再动手。
- 快照是“基线”，不是“首次接入那一刻的原件”：每次 `apply` 会把账号文件里新增的行并入基线（只增不删），所以 `restore` 通常能保住手写内容；但如果你改完文件没跑过 `apply`，`restore` 会用旧基线盖掉这次改动。
- 没有快照时 `restore` 直接报 `no_snapshot`，不写入任何内容。

## 不做什么

- **不物理合并账号文件。** 没有“A 覆盖 B”，也不存在把所有 `MEMORY.md` 拼成一份文件。
- **不做语义合并。** 只合并 ≥0.90 的近重复，且数字序列必须一致（`30s` 与 `60s` 是两条事实）。措辞不同的一律当两条——宁可漏合并，不误删。
- **不删账号原文。** `forget` 只动共享库；`restore` 也是用快照覆盖，不删文件。
- **不改人格。** `collect` / `apply` 只碰 `MEMORY.md`；SOUL / USER 只有 `rebalance --apply` 会追加受管段落；`IDENTITY.md` 不写。
- **不碰工作区记忆与分片记忆。** 没有对应实现。
- **不发布事实。** 见[为什么只发布规则](#为什么只发布规则不发布事实)。
